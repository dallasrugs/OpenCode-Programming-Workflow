# Evidence and efficiency prompt tuning v3

Task-agnostic prompt-body updates based on the [PocketCalc review](2026-11-01-calculator-session-reflection.md) and [EmberText review](2026-11-01-embertext-session-reflection.md), installed on 2026-11-01 in both the repository and global OpenCode agents. The successful discovery v2 behavior is retained. These changes aim to improve accuracy and efficiency; no post-change effectiveness result is claimed.

## Evidence → intervention

| Observed behavior | General prompt intervention |
| --- | --- |
| Reviewer duplicated calculator checks, build and packaging despite assigned test ownership. | Inspect candidate-linked evidence first; independent reasoning does not require independent full-suite execution. A new targeted check needs an unresolved concern and assigned owner. |
| Supplementary calculator scripts copied engine code and printed assertion mismatches while the report generalized that checks passed. | Exercise the delivered artifact. Report failed attempts and mismatches even with exit zero; copied implementations are not product verification. |
| Reviewer withdrew the wrong explanation for a Tk count issue but overlooked its actual `None` output in an ordinary zero-offset state. | Reconcile contradictory output before approval or withdrawal. Disproving a theory does not prove the workflow works. Distinguish zero, empty and missing results in normal states. |
| Initial and boundary states were absent from otherwise useful widget tests. | Coder and planner select discriminating initial/empty, boundary, repeated-use and recovery cases from actual action transitions. |
| Reviewers made unsupported API-default and severity claims and proposed broad catches or weakening file protections. | Verify defaults from available authoritative evidence, separate confirmed/suspected/withdrawn/unverified findings, and require a demonstrated need for changes that weaken safety. |
| Researcher probed protected Git paths and entertained low-value interpretations despite relevant request context. | Use ordinary named evidence, stop at an established empty scope, interpret terms in context and ask only questions that change the next decision. |
| Poseidon usefully challenged false findings and caught a stale calculator bundle. | Preserve that behavior; give disputed findings explicit dispositions and align final evidence and artifacts with the final candidate. |

## Role changes

- **Reviewer:** Largest targeted change: actual-module verification, candidate-linked evidence reuse, output-versus-exit-status checks, contradiction handling, calibrated findings and bounded verdicts.
- **Coder:** Tests follow real action states, including ordinary boundaries; repaired defects retain a reproducer. Handoffs identify the candidate, commands, failures/skips and verification limits. Stale deliverables are called out.
- **Researcher:** Contextual interpretation and decision-value findings; no protected-path fishing or fabricated platform preferences.
- **Maintainer:** Reuse feasibility findings, propose the smallest next check, and distinguish dependency count, compilation, runtime operation, packaging and measured resources.
- **Team Lead:** Plan minimal slices and discriminating checks with an explicit owner. In the repository's primary role, also reconcile disputed evidence and avoid duplicate validation.
- **Poseidon:** Preserve confirmed intent and the question-answer gate. In the installed primary role, reuse current evidence, scrutinize review withdrawals and refresh stale delivery artifacts once. Its repository worker version routes checks through Team Lead.

No application-specific condition or fix was added to a shared prompt. The known EmberText Find defect was not repaired by this prompt update. No new skill import, model replacement, permission change, runtime change or hierarchy migration was performed. Native skills remain unchanged.

## Measuring the next iteration

Frozen local benchmark candidate **evidence-v3** and baseline **discovery-v2** have identical models, permissions, modes, runtime, skills, cases, rubric, scorer and harness. Only prompt bodies differ. Earlier snapshots and reviews were preserved. No scored v3 runs exist.

Use the same requirements, initial artifact, environment and predeclared user decisions when preparing paired trials. Continue scoring actual task outcomes and critical journeys with the existing rubric. Also retain descriptive evidence of unnecessary repeated checks, supported versus refuted findings, known missed defects, correction cycles and unsupported completion claims. Do not infer fewer missed defects simply from fewer reported findings, or efficiency simply from fewer tool calls. Unresolved findings stay unresolved; only adjudicated claims can be counted as correct or incorrect.

For meaningful transfer, try new tasks in addition to these development examples. Keep simple precise tasks in the set to detect excessive questioning or role overhead. Multiple turns or screenshots of one project are not independent samples. Two positively reviewed projects motivated these changes; they do not establish a statistically measured improvement.

Start a fresh OpenCode session to test the installed prompts. Prepare the benchmark run before agent edits and retain questions, answers, source changes, actual validation output and hands-on feedback.
