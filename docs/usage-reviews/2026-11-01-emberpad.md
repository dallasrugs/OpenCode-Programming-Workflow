# Outcome-based prompt tuning from the Emberpad review

Date: November 1, 2026. Scope: six agent prompt bodies and assessment artifacts.
The earlier infrastructure/evaluation assignment remains paused. No editor source,
model, provider, permission, role authority or runtime budget was changed by this
prompt-tuning step. No live model request was made.

## Original request, scores and clarification

The request was an original Notepad++-inspired editor for text/code, linting,
snippets and important features, with upstream as a reference rather than an exact
copy. The original request did not settle a delivery platform. The user's review
explains that choosing a browser without asking missed their expectation.

| User assessment | Recorded score / 10 |
|---|---:|
| Interface | 8 |
| Usability | 4 |
| Intended internal-save workflow | 0 |
| Discoverable filename/extension choice | 0 |
| Overall | 4 |

Agent-specific user scores remain: Poseidon 3, Team Lead 6, Researcher 8,
Coder initial 6.5, Reviewer initial 7, Coder revision 6. No numeric score was given
for the final Reviewer response. These are user judgments on this task, not new
population grades. Revisions/screenshots are correlated observations of one task.
The overall 4 is preserved as supplied; it is not an arithmetic average invented
from other ratings.

The subsequent user clarification is authoritative for this product:
**Save commits document state within the app's in-memory workspace; Download
exports a copy to the device.** Naming/extension should be available in that
workflow. Persistence across reloads is a distinct decision; neither disk writing
nor browser storage is silently added to that definition. This lesson does not
make every future application's Save action an in-memory operation.

## Evidence and failure mechanism

The supplied agent transcript shows Poseidon choosing a browser because the folder
was empty and platform unspecified. Team Lead inherited the assumption and adopted
import/download as the file workflow, then declared that no user decision blocked
implementation. The initial mistaken premise crossed the handoff boundary.

The user supplied three screenshots, which support judgments about the visible
interface, dirty tabs, a download notification and a small pencil control. They do
not prove the entire click/cancel/error sequence.

Read-only inspection of the current app's `src/App.tsx` found:

- `newFile()` creates and activates an in-memory document. The source does not show
  an automatic download from that handler. The reported confusing experience is
  retained as user feedback, not converted into a proven auto-download defect.
- `save()` creates a Blob/download anchor, triggers it, then marks the document
  saved. That behavior conflicts with the user's clarified internal-save meaning.
- `rename()` accepts a name including its extension through a pencil-triggered
  prompt. The capability exists in code; the user still could not discover/use the
  desired identity-choice workflow. A code-presence check cannot refute that UX
  failure or establish that the full workflow is usable.

The reviewed source hash is recorded in the JSON review fixture. The editor was
not modified. Source inspection is not a browser interaction test.

The Researcher contributed a visual direction the user liked. Retain that strength
without treating its proposed shortcuts, persistence or export behavior as user
requirements. The Coder followed a narrowed plan and disclosed limitations; the
failure is distributed across discovery, planning, implementation and acceptance.
Reviewer caught some genuine concerns, but a unit/SSR recheck did not prove the
complete editing workflow in a real runtime. A large bundle warning also does not
by itself establish actual runtime memory consumption.

## General prompt changes

Each role gets one bounded, replaceable outcome-coverage section (115–149 words),
not application-specific repair instructions. No product names, source paths or
mandatory technology choices enter shared prompts.

| Role | General correction |
|---|---|
| Poseidon | Clarify consequential delivery/state choices; use permitted grilling for ambiguous products; record behavioral semantics alongside visuals |
| Team Lead | Challenge inherited assumptions; map requirement → owner → observable check → evidence; deliver critical vertical slices first |
| Researcher | Research capability fit; distinguish user intent, evidence and proposals, and missing versus undiscoverable controls |
| Maintainer | Check architecture against confirmed jobs; separate working state, commit, persistence and external effects; measure relevant performance |
| Coder | Implement complete action/result flows, preserve state/identity, expose essential choices and test unintended effects/cancellation |
| Reviewer | Review original intent and primary journeys before polish; separate code plausibility, unit coverage and real interaction proof |

Conditionality matters. A research memo needs evidence/outcome validation, not file
naming controls. An API change needs contract and side-effect checks, not a new UI.
A small precise fix needs no product-discovery interview. Explicit platform or
creative delegation is reused rather than questioned repeatedly. The prompts
require the meaning of an action to follow the user, not the current training case.

## Statistical evaluation protocol

The prospective rubric is frozen in `tests/usage_reviews/rubric-v1.json`:
intent alignment 20%, core behavior 30%, workflow/usability 25%, reliability and
evidence 15%, presentation 10%. These are assessor-proposed future weights, not
weights attributed to this user. A failed critical criterion blocks readiness even
with a high average. Unverified critical behavior is inconclusive, not a pass.
Missing ratings stay missing; do not create a synthetic overall score.

The standard-library scorer `tests/agent_evals/grade_usage_review.py` separates:

1. User-provided overall/product ratings, preserved verbatim.
2. Criterion statuses and attributable evidence/verification gaps.
3. An optional weighted score when all prospective dimensions were assessed.
4. Paired before/after runs, aggregated within a distinct task before comparing
   tasks, so ten repeats/screenshots/assertions do not masquerade as ten tasks.

With at least five distinct non-tied scored task clusters it can report an exact
two-sided sign test. Independence, task preselection, comparable conditions and
consistent assessment remain prerequisites; a p-value is not proof of general
improvement. Under five such tasks it emits no significance claim. Do not pool
unlike product dimensions or role-specific scores as independent samples.

For future evaluation, freeze requests/rubrics before seeing candidate output,
keep model/environment/test ownership comparable, retain failures, and separate
practice cases from transfer cases. The six transfer scenarios in
`tests/usage_reviews/transfer_cases_v1.json` are PREPARED_NOT_RUN and include web,
API, automation, database and research work. Do not tune their expected checks
merely because a run fails. No new product score or agent-grade improvement is
claimed: sample size is one reviewed task, and post-tuning product sample size is
zero.

## Installation and verification

The same outcome-method sections were staged for the repository's six prompts and
the active global six prompts. Existing prompt bodies and native frontmatter were
preserved; existing authority differences between those installations were not
migrated. Sections have stable markers and replace in place on a later tuning pass.
Global installation is backed up before atomic writes. Hash manifests record the
before/after prompt bodies and unchanged frontmatter.

Deterministic checks validate rubric arithmetic, critical failure gating, missing
ratings, repeated-task clustering, exact sign-test arithmetic and malformed inputs.
Native skill/config validation remains separate from behavioral effectiveness.
No assertion that a phrase exists in a prompt is counted as an improved outcome.
Nvidia limits remain 20 requests/minute and 1,000/day; this tuning performs no live
model evaluations. Updated prompt discovery and the exact verification summary
are recorded with the installation manifest. Existing application defects require
a subsequent implementation task; editing prompts does not repair the shipped app.

Final verification: 77 Python tests ran, 72 passed and five opt-in live permission
checks were skipped. Skill/config validation and diff whitespace checks passed.
Actual OpenCode agent discovery in the app project confirmed all six global
prompts contain the tuned section, with the existing global Poseidon-primary
authority/model configuration intact. Prompt/native metadata hashes were preserved
for all twelve edited definitions. These checks verify installation and assessment
logic; task effectiveness after tuning remains NOT_RUN.
